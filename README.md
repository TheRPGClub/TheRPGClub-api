# RPGClub API

## Stack

- Ruby 3.4
- Rails 8.1 API mode
- PostgreSQL
- Warden for authentication
- Discord OAuth for browser login
- Optional bearer-token service auth for the Discord bot

## Local development

Copy `.env.example` to `.env`, then prepare the app once:

```sh
docker compose up -d db
ruby bin/setup --skip-server
docker compose stop db
```

After that, `script/dev` is the only command needed to work on the app. It
starts the PostgreSQL container, waits for it to report healthy, runs the Rails
server, and stops the container again when you quit:

```sh
script/dev          # extra arguments are forwarded to `bin/rails server`
```

The Compose service deliberately has no restart policy, so the container never
comes back by itself when Docker starts at boot. `ruby bin/dev` still boots the
server alone, for when the database is already running.

PostgreSQL is published on host port `5433` by default to avoid colliding with
a native PostgreSQL installation. Both port settings in `.env.example` must
stay aligned if you change it.

The Compose service creates two databases in its persistent volume:

- `rpgclub_api_development` contains the sample users, games, taxonomy,
  collection activity, and GOTM voting rounds from `db/seeds/development.rb`.
- `rpgclub_api_test` is isolated scratch space for RSpec. Test configuration
  ignores `DATABASE_URL` and refuses to boot unless its database ends in
  `_test`.

Run the suite with the database up (`script/dev` in another terminal, or
`docker compose up -d db`):

```sh
ruby bin/rails db:test:prepare
bundle exec rspec
```

Database structure is tracked in Rails' standard `db/schema.rb`. Commit schema
changes generated by `ruby bin/rails db:migrate` together with their migration.
Development seeds are idempotent and can be refreshed at any time with
`ruby bin/rails db:seed`.

The seeds build three GOTM / Non-RPG GOTM rounds — two finished ones with
nominations, ballots and winners, plus a current one. Nominating and voting are
mutually exclusive phases of a round (nominations close when that round's vote
opens), so `SEED_VOTING_PHASE` picks which one "now" sits in:

```sh
ruby bin/rails db:seed                              # round 3 voting is open
SEED_VOTING_PHASE=nominating ruby bin/rails db:seed # round 4 nominations are open
```

Switching phases and re-seeding removes the rows the other phase left behind.

Winners come out of a seeded RNG rather than the nomination lists, so the seeds
filter instead of curate: a game that won a round is dropped from the fields of
every later round, and a re-seed rebuilds the seeded accounts' ballots from
scratch so the tally does not drift. The run asserts both, plus that GOTM rounds
2 and 3 keep enough nominations for the larger vote cap, and fails loudly if an
edit to the lists breaks either.

## Steam Web API key

Steam library imports call the Steam Web API through `Steam::Client`, which
reads its key from `STEAM_WEB_API_KEY` (`STEAM_API_KEY` is accepted as a
fallback, matching the Discord bot). Get a key at
<https://steamcommunity.com/dev/apikey>, put it in `.env` for local work, and
set it on Fly as a secret rather than in `fly.toml`:

```sh
fly secrets set STEAM_WEB_API_KEY=<key>
```

Specs never call Steam: they stub HTTP through the client's injected Faraday
connection.

## Google Custom Search (HowLongToBeat)

HLTB lookups (`POST /api/v1/games/:id/hltb/lookup`, `Hltb::Client`) find a
game's HowLongToBeat page through Google Custom Search, as the Discord bot
does. Set `GOOGLE_CUSTOM_SEARCH_API_KEY` (a Google API key with the Custom
Search API enabled) and `GOOGLE_CUSTOM_SEARCH_ENGINE_ID` (the Programmable
Search Engine id); the bot's `GOOGLE_API_KEY` and `SEARCH_ID` are accepted as
fallbacks. Without them a lookup answers 503 `hltb_not_configured`.

```sh
fly secrets set GOOGLE_CUSTOM_SEARCH_API_KEY=<key> GOOGLE_CUSTOM_SEARCH_ENGINE_ID=<id>
```
